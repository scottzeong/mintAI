# 리서치 자료 구조 명세

**v1.0 · 2026-07-25 · [`MVP.md`](MVP.md) §4의 하위 문서**

> 이 문서는 Digest 좌측에 표시되는 **휘발성 자료**의 형식을 정한다.
> 카드(영구)의 형식이 아니다. 카드는 여전히 사람이 자유롭게 쓴다.

---

## 0. 왜 구조를 넣는가

기존 §4 규격은 "요점 3~5개 + 다른 관점"이 전부였다. 질문의 성격과 무관하게
같은 모양이 나온다. 그런데 **"신뢰란 무엇인가"와 "신뢰가 거래비용을 줄이는가"는
알아야 할 것이 다르다.** 전자는 경계와 정의가, 후자는 메커니즘과 근거 강도가 핵심이다.

같은 틀에 넣으면 둘 다 반쯤만 답한다.

### 0.1 ⚠ 1,200자 → 3,000자 — 무엇을 거는가

§4는 출력을 **1,200자 이내**로 제한했다. 이유는 R1(소화 병목) 방지였다:
길면 읽는 데 부담이 생기고, "나중에 읽자"가 되고, 대기 큐가 쌓인다.

3,000자는 그 판단을 2.5배 뒤집는 것이다. **근거는 하나다:**

> **뭉텅이 산문 1,200자는 처음부터 끝까지 읽어야 한다.
> 구획된 3,000자는 골라 읽을 수 있다.**

즉 걸고 있는 것은 분량이 아니라 **구조가 실제로 선택적 읽기를 가능하게 하는가**다.
이게 틀리면 `avg_queue`(§8)가 먼저 나빠진다. 그때는 분량이 아니라 **구조를 의심**해야
한다 — 섹션이 너무 잘게 쪼개졌거나, 섹션 제목이 내용을 예고하지 못하는 것이다.

**측정을 위해 `research_runs.chars` 를 남긴다.**
소화·폐기 시 `output_md` 는 NULL 이 되므로 길이를 사후에 잴 수 없다.
§2.2에서 배운 것과 같은 교훈이다 — **나중에 알고 싶어질 수는 지금 남겨야 한다.**

## 1. 질문 유형 (8종)

모델이 질문을 읽고 **하나**를 고른다. 사용자에게 고르게 하지 않는다 —
§3.1의 "마찰 제로" 원칙에 어긋난다.

| 코드 | 유형 | 대표 질문 형태 |
|---|---|---|
| `concept` | **개념** | "X란 무엇인가", "X의 의미는" |
| `causal` | **인과·관계** | "X가 Y에 영향을 주는가", "왜 X면 Y인가" |
| `history` | **역사·전개** | "X는 어떻게 변해왔나", "X의 기원" |
| `person` | **인물** | "X는 누구인가", "X의 사상" |
| `event` | **사건** | "X 사건이란", "X는 왜 일어났나" |
| `compare` | **비교·대조** | "X와 Y의 차이", "X 대신 Y를 쓰면" |
| `data` | **현황·데이터** | "지금 X는 얼마나", "최근 추세" |
| `debate` | **논쟁** | "X에 대한 찬반", "X는 정당한가" |

**8종인 이유:** 더 줄이면 서로 다른 것이 한 틀에 섞이고, 더 늘리면 분류가 흔들린다.
경계가 애매하면 **더 구체적인 쪽**을 고른다 (예: "마키아벨리의 권력관" → `person`,
"권력이란 무엇인가" → `concept`).

## 2. 유형별 구조

모든 유형에 **공통 섹션 2개**가 붙는다 (§2.9).
분량 배분은 3,000자 기준이며, 섹션당 400~600자.

### 2.1 `concept` — 개념

```
## 정의
## 구성 요소        무엇이 있어야 X 인가
## 무엇이 아닌가 ★  흔히 혼동되는 인접 개념과의 경계
## 쓰이는 자리      실제 용례 2~3
## 정의가 갈리는 지점  학파·분야별로 다르게 쓰는 부분
```

★ **"무엇이 아닌가"가 이 유형의 핵심이다.** 대중서에서 개념 오용은 대개 정의를
몰라서가 아니라 **경계를 몰라서** 생긴다. "신뢰"와 "호감", "권력"과 "권위"의 차이.

### 2.2 `causal` — 인과·관계

```
## 주장되는 관계     X → Y 를 한 문장으로
## 메커니즘 ★       어떤 경로로 작동한다고 보는가 (단계별)
## 근거의 강도 ★    상관인가 / 실험인가 / 사례인가. 표본과 맥락
## 교란 요인·반례    이 관계를 흔드는 것
## 성립 조건        언제 성립하고 언제 깨지는가
```

★ **메커니즘과 근거 강도를 반드시 분리한다.** 대중서에서 가장 흔한 사고는
상관을 인과처럼 쓰는 것이다. 근거가 상관뿐이면 그 사실이 눈에 보여야 한다.

### 2.3 `history` — 역사·전개

```
## 시기 구분        3~5 국면, 각 국면의 이름
## 전환점 ★         무엇이 언제 왜 바뀌었나 (계기)
## 지속된 것        바뀌지 않은 것 — 이게 종종 더 중요하다
## 현재 상태
## 통설과 수정주의   교과서 서술과 최근 연구의 차이
```

★ **연표 나열이 아니다.** "1970년에 A, 1985년에 B"는 정보이지 이해가 아니다.
전환의 **계기**가 있어야 글로 쓸 수 있다.

### 2.4 `person` — 인물

```
## 한 줄 규정       이 사람을 한 문장으로
## 좌표            시대·지역·소속. 최소한만
## 핵심 기여 2~3    무엇을 바꿨나
## 무엇에 반대했나 ★ 그가 싸운 상대 — 사상은 대개 반대 속에서 선명해진다
## 평가의 변천      당대 평가 → 현재 평가
## 비판과 논쟁
```

★ **위인전이 되지 않게 하는 장치다.** 누구와 무엇에 맞섰는지가 없으면
그 사람의 주장이 왜 필요했는지 알 수 없다.

### 2.5 `event` — 사건

```
## 사실 골격        언제·어디서·누가·무엇을 (건조하게)
## 직전 배경        왜 그 시점이었나
## 전개
## 결과와 파급
## 해석의 대립 ★    같은 사실을 두고 갈리는 설명
## 사실이 불확실한 지점 ★  아직 확정되지 않은 것
```

★ **사실과 해석을 분리한다.** 이게 섞이면 대중서에서 가장 위험하다 —
독자는 해석을 사실로 읽는다. 확정되지 않은 것을 확정된 것처럼 쓰지 않기 위해
"불확실한 지점"을 따로 받는다.

### 2.6 `compare` — 비교·대조

```
## 비교 축 ★        무엇을 기준으로 비교하는가 (3~4개)
## 축별 대조        표 형태
## 공통 오해        흔히 잘못 알려진 차이
## 어느 쪽이 언제   상황별 우열
## 이분법이 깨지는 지점 ★  사실은 둘로 나뉘지 않는 부분
```

★ **축을 먼저 세우지 않으면 사과와 오렌지를 비교하게 된다.**
그리고 대부분의 이분법은 어딘가에서 무너진다 — 그 지점이 글감이 된다.

### 2.7 `data` — 현황·데이터

```
## 핵심 수치 ★      반드시 기준 시점 명시
## 측정 방법과 한계 ★  무엇을 어떻게 셌는가
## 추세
## 집단·국가 간 차이
## 수치가 오도할 수 있는 지점
```

★ **시점과 측정 방법이 없는 수치는 쓸모없다.** "실업률 3%"는 무엇을 실업으로
세느냐에 따라 두 배씩 달라진다. 대중서에서 통계 오용을 막는 유일한 방법은
숫자 옆에 항상 방법을 붙이는 것이다.

### 2.8 `debate` — 논쟁

```
## 쟁점 정식화      정확히 무엇을 두고 다투는가
## 합의된 사실 ★    양측이 동의하는 부분 — 먼저 밝힌다
## 입장 A          핵심 주장 + 근거
## 입장 B
## 실제 갈라지는 지점 ★  사실 판단인가, 가치 판단인가
## 제3의 입장
```

★ **"무엇에 동의하는가"를 먼저 쓰면 논쟁의 실체가 드러난다.**
대개 사실은 합의돼 있고 가치에서 갈린다. 그걸 구분하지 못한 글은
상대를 무지하다고 쓰게 되고, 그런 대중서는 설득력이 없다.

### 2.9 공통 섹션 (전 유형)

```
## 다른 관점        기존 §4 요구사항. 유지
## 확실하지 않은 것 ★  모델이 자신 없는 지점을 명시
```

★ **"확실하지 않은 것"을 강제하는 이유:** 모델은 기본적으로 확신에 찬 문장을
쓴다. 저술가가 그걸 그대로 믿으면 출간물에 오류가 들어간다.
**어디를 더 확인해야 하는지가 보여야 파이프라인이 루프가 된다** (원칙 3).

## 3. 넣지 않는 것

**"이걸 카드로 만든다면 이런 각도" 같은 요약 제안은 넣지 않는다.**

편해 보이지만 H1을 정면으로 오염시킨다. 요약의 각도를 AI가 정해주면,
사람이 하는 일은 그걸 받아쓰는 것으로 줄어든다. 그건 이 도구가 검증하려는
바로 그 행위를 대신해버리는 것이다.

자료는 **재료**까지만 준다. 무엇을 뽑을지는 사람이 정한다.

## 4. 구현 형태

### 4.1 분류는 별도 호출 없이

모델이 한 번의 호출 안에서 유형을 고르고 그 구조로 출력한다.
분류용 호출을 따로 두면 지연과 비용이 두 배가 되는데, 정확도 이득은 크지 않다.

출력 **첫 줄**에 유형을 선언하게 한다:

```markdown
> **유형:** 인과·관계

## 주장되는 관계
...
```

인용구로 두면 마크다운에서 자연스럽게 보이면서 파싱도 쉽다.
파싱에 실패하면 `kind = null` 로 두고 자료는 그대로 쓴다 —
**분류는 부가 정보이지 자료의 조건이 아니다.**

### 4.2 스키마

```sql
alter table research_runs add column kind  text;   -- concept | causal | ... | null
alter table research_runs add column chars int;    -- 폐기 후에도 남는 길이
```

`kind` 를 저장하면 **유형별 폐기율**을 볼 수 있다. 특정 유형에서만 자료가
쓸모없다면 그건 H1 문제가 아니라 그 유형의 프롬프트 문제다 (§3.5와 같은 논리).

### 4.3 화면

Digest 좌측 상단에 유형 뱃지를 단다. 섹션이 많아지므로
`## ` 제목이 본문과 뚜렷이 구분되어야 한다 — `prose` 스타일은 이미 적용돼 있다.

## 5. 판정

이 변경이 옳았는지는 §8 지표로 읽는다.

| 신호 | 해석 |
|---|---|
| `avg_queue` 상승 | 3,000자가 부담이다 → **구조를 의심**한다 (분량이 아니라) |
| `discard_rate` 상승 | 특정 유형의 프롬프트 문제 → `kind` 별로 쪼개 본다 |
| 카드 수 증가 | 재료가 늘어 카드가 나온다 → 성공 |
| 카드 수 그대로, 큐만 증가 | **자료는 많은데 소화가 안 된다** — 가장 나쁜 신호 |

마지막 줄이 나오면 되돌린다. 되돌리기는 쉽다 — 프롬프트 하나다.
