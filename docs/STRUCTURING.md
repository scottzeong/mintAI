# Structuring — 카드에서 책으로

**v1.0 · 2026-07-25 · [`MVP.md`](MVP.md) §9의 "1. 목차 + 카드 배치" 복귀**

> Library 의 카드를 재료로 **책의 구조**를 제안받고, 확정한 구조 위에서
> 챕터별로 집필한다.

---

## 0. ⚠ 먼저 정해야 하는 것 — 목차는 산문인가

**원칙 1:** *영구 저장되는 산문은 100% 인간이 타이핑한 것.*

AI가 제안한 챕터 제목이 DB 에 저장되는 순간 이 원칙이 걸린다.
지금까지는 피할 수 있었다 — Digest 는 AI 문장을 폐기했고, Write 에는 초고 생성이
없었다. **Structuring 은 피할 수 없다.** 목차 없이는 이 기능이 성립하지 않는다.

### 0.1 세 가지 선택지

| | 방식 | 문제 |
|---|---|---|
| A | AI 제목을 그대로 저장 | 원칙 1이 조용히 무너진다. 몇 달 뒤 "이 제목 내가 지었나?"를 알 수 없다 |
| B | 사람이 전부 다시 타이핑해야 저장 | 마찰이 과하다. 20개 챕터 제목을 옮겨 적는 건 소화와 달리 **생각을 만들지 않는다** |
| C | **AI 원안과 내 제목을 나란히 보관** | 구현이 조금 늘어난다 |

### 0.2 결론: C

```sql
chapters (
  title           text not null,   -- 실제 쓰는 제목 (사람이 언제든 고친다)
  proposed_title  text,            -- AI 원안. 절대 덮어쓰지 않는다
  ...
)
```

confirm 시 `title := proposed_title` 로 복사된다. 그 뒤 사람이 고치면 둘이 갈라진다.

**이 설계가 주는 것:**

1. **"이 제목은 내가 쓴 것인가"를 언제나 알 수 있다.** 원칙 1이 지키려던 것은
   *AI 문장을 내 것으로 착각하지 않는 것*이었다. 폐기가 아니라 **표시**로도 지킬 수 있다.
2. **계측이 된다.** `title <> proposed_title` 인 챕터의 비율 = 구조를 얼마나
   내 것으로 만들었는가. 이게 0에 가까우면 **AI가 짠 책을 받아쓰고 있는 것**이다.

> **원칙 1을 고쳐 쓴다:**
> ~~영구 저장되는 산문은 100% 인간이 타이핑한 것~~
> → **영구 저장되는 산문은 100% 인간이 타이핑한 것.
>   구조(목차)는 AI가 제안할 수 있으나, 원안과 내 수정본이 항상 구분되어야 한다.**
>
> **본문(`body_md`)에는 이 완화가 적용되지 않는다.** 챕터 본문은 여전히
> 100% 사람이 쓴다. AI 초고 생성은 §9의 3번으로 계속 유예한다.

## 1. 흐름

```
Library                          Write
┌──────────────────┐            ┌────────────────────────────┐
│ [Structuring]    │            │ 좌: 챕터별 카드            │
│   ↓ 30~60초      │            │ 우: 챕터 제목 + 본문 입력  │
│ 제안 3개 제시    │  confirm   │     [Save]                 │
│   ↓ 하나 선택    │ ─────────► │                            │
│ [Confirm]        │            │ 책 제목으로 관리           │
└──────────────────┘            └────────────────────────────┘
```

### 1.1 왜 제안을 3개 하는가

제안이 하나면 **그럴듯하다는 이유로 그냥 받아들이게 된다.** 앵커링이다.
셋을 나란히 놓으면 비교가 강제되고, 그 순간 *"내가 쓰고 싶은 책은 무엇인가"* 를
스스로 판단하게 된다.

각 제안은 이렇게 구성된다:

```
제목
한 줄 논지          이 책이 주장하는 것
누구를 위한 책인가
챕터 5~9개          제목 + 한 줄 요지 + 배치될 카드
제외한 카드와 이유 ★
```

### 1.2 ★ 제외한 카드를 반드시 밝힌다

"일부 자료는 포함하지 않는다"는 요구는 옳다. **다만 이유 없이 빠지면 안 된다.**
이유가 없으면 "왜 내 카드가 사라졌지?"가 되고, 사용자는 제안을 신뢰하지 못한다.

```json
"excluded": [
  { "card_id": 12, "reason": "이 책의 논지와 층위가 다름 — 별도 주제" },
  { "card_id": 31, "reason": "7장 내용과 중복" }
]
```

**제외 비율 자체가 신호다.**

| 제외율 | 해석 |
|---|---|
| 낮음 (< 20%) | 카드가 한 주제로 모여 있다 |
| 높음 (> 50%) | **책 하나로 묶이지 않는다** — 카드가 산만하거나, 아직 두 권 분량이 섞여 있다 |

후자라면 제안을 받아들이기 전에 **컬렉션으로 먼저 갈라내는 게 맞다** (§3.6).

### 1.3 최소 카드 수

**50장 미만이면 버튼을 비활성화한다.**

카드 5장으로 책 구조를 제안받으면 우스운 결과가 나오고, 그 우스운 결과가
"이 기능은 쓸모없다"는 인상을 만든다. §1.2가 캔버스를 유예한 것과 같은 논리다 —
**기능의 가치가 데이터 양에 비례하면, 데이터가 모이기 전에는 보여주지 않는다.**

비활성 상태에서는 남은 장수를 보여준다: *"책 구조를 제안하려면 카드가 50장 이상
필요합니다 (현재 8장)"*.

## 2. AI 제안의 휘발성

**Digest 와 같은 패턴을 쓴다.**

```
structuring_runs.output_json   ⚠ 휘발성
  └ confirm → 채택된 제안만 works/chapters/chapter_cards 로 승계
             나머지 2개 제안은 output_json = NULL 로 폐기
```

채택되지 않은 제안은 **쓰이지 않은 AI 산문**이다. 남길 이유가 없다.
채택된 것도 산문 자체가 넘어가는 게 아니라 **구조(제목·배치)만** 넘어간다.

`chars`, `model`, `ran_at` 은 남긴다 — Digest 에서와 같은 이유로,
나중에 "제안이 쓸 만했는가"를 재려면 필요하다.

## 3. 스키마 (초안)

```sql
create table works (
  id          bigint primary key,
  user_id     uuid,
  title       text not null,        -- 책 제목. 이걸로 관리한다
  thesis      text,                 -- 한 줄 논지
  audience    text,
  status      text default 'writing',  -- writing | done | abandoned
  created_at  timestamptz
);

create table chapters (
  id              bigint primary key,
  work_id         bigint references works(id) on delete cascade,
  seq             int not null,     -- 순서
  title           text not null,    -- 내가 쓰는 제목
  proposed_title  text,             -- ★ AI 원안. 덮어쓰지 않는다 (§0.2)
  gist            text,             -- 한 줄 요지 (AI 원안, 참고용)
  body_md         text default '',  -- ★ 본문 — 100% 사람이 쓴다
  updated_at      timestamptz,
  unique (work_id, seq)
);

create table chapter_cards (
  chapter_id  bigint references chapters(id) on delete cascade,
  card_id     bigint references cards(id)    on delete cascade,
  seq         int,
  primary key (chapter_id, card_id)
);

create table structuring_runs (
  id          bigint primary key,
  user_id     uuid,
  output_json jsonb,                -- ⚠ 휘발성
  card_count  int,                  -- 제안 당시 카드 수
  model       text,
  chars       int,
  ran_at      timestamptz,
  purged_at   timestamptz,
  error       text
);
```

**`chapter_cards` 가 카드를 삭제하지 않는다.** 카드는 여러 책에 동시에 쓰일 수 있다 —
§3.6의 다차원 분류와 같은 원칙이다. 책은 카드에 대한 **하나의 배치**일 뿐이다.

---

## 4. `drafts` 는 어떻게 되는가

**없애지 않는다.** 짧은 글(에세이·칼럼)은 `drafts`, 책은 `works`.

§8의 `long_drafts`(800자 글 1편)가 `drafts` 를 재고 있다. 이걸 갈아엎으면
진행 중인 판정 기준이 흔들린다. Write 화면을 두 모드로 나눈다:

```
Write ─┬─ 낱글      → drafts     (기존 그대로)
       └─ 책        → works      (Structuring 확정 시 생성)
```

## 5. ⚠ H2 검증에 미치는 영향

H2 = *"카드가 쌓이면 글쓰기가 실제로 쉬워지는가."*

Structuring 은 글쓰기를 확실히 쉽게 만든다. **그런데 무엇 덕분에 쉬워졌는지가
흐려진다** — 카드 덕분인지, AI가 구조를 짜줬기 때문인지.

§3.4에서 AI 초고를 뺀 것과 정확히 같은 문제다. 다만 이번엔 **본문이 아니라
구조**라서 침습성이 덜하고, 무엇보다 사용자가 원하는 기능이다.

**계측으로 구분한다:**

| 지표 | 의미 |
|---|---|
| `title <> proposed_title` 비율 | 구조를 얼마나 내 것으로 만들었나 |
| 카드 재배치 횟수 | 제안을 그대로 썼나, 뜯어고쳤나 |
| 제외 카드 되살린 수 | AI 판단을 검토했나 |

이 셋이 전부 0에 가까우면 **AI가 짠 책을 받아쓰고 있는 것**이고,
그때 H2는 "카드가 쌓여서"가 아니라 "AI가 대신 해줘서" 참이 된 것이다.
그건 다른 도구다.

## 6. 확정된 결정 (2026-07-25)

| # | 결정 | 근거 |
|---|---|---|
| 1 | **제안 3개** | 하나면 그럴듯하다는 이유로 받아들이게 된다 (앵커링). 한 번의 호출로 3개를 생성하므로 비용은 3배가 아니다 |
| 2 | **자동저장으로 통일** | 화면 하나에서 한쪽은 자동, 한쪽은 수동이면 언젠가 잃는다. `Save` 버튼 대신 800ms 자동저장 + 저장 상태 표시 (Write 와 동일) |
| 3 | **전체 카드 대상** | 필터 결과로 좁히면 "지금 보고 있는 것"과 "제안 대상"이 달라 혼란스럽다. 좁히고 싶으면 제안을 받은 뒤 챕터에서 뺀다 |
| 4 | **최소 50장** | 15장은 너무 낮았다. 책 한 권을 논하려면 그 정도는 쌓여야 하고, PRD §9도 "카드 50장 넘으면"을 관계 링크의 조건으로 뒀다 |

### 6.1 자동저장으로 바꾼 이유 (요구사항과 다름)

원 요구사항에는 `Save` 버튼이 명시됐다. 자동저장으로 바꾼 이유:

Write 화면은 이미 800ms 자동저장이다. 같은 앱에서 낱글은 자동 저장되는데 챕터는
버튼을 눌러야 한다면, **언젠가 반드시 누르지 않고 탭을 닫는다.** 저술 도구에서
문장을 잃는 것은 착상을 잃는 것 다음으로 나쁘다.

대신 저장 상태를 항상 보이게 한다 — `저장 중… / 자동저장 ✓`.
버튼이 없어도 "저장됐다"는 확신은 있어야 한다.

## 7. 남은 것 (이번 구현 범위 밖)

- **재구조화** — 카드가 더 쌓인 뒤 다시 제안받기. 기존 `works` 갱신 vs 신규 생성
- **챕터 순서 변경** — 드래그앤드롭. §3.6과 같은 이유로 유예
- **소스 추적성** — 챕터 → 카드 → 착상 → 출처 역추적 (별도 기능으로 예정)
